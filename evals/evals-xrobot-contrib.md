# Evals: `xrobot-contrib` (contributor skill)

Baseline: LibXR v2.0.1 / xrobot 1.0.1 / libxr (CodeGenerator) 6.0.1 / VS Code extension 2.0.1.
Each eval is run in an agent with this skill installed. The environment has no hardware and
no push access; where the skill directs an external action, the expected behavior is to
state the exact action and stop.

| # | Question | Expected behavior |
| --- | --- | --- |
| C1 | Add an ADC driver for HPM. | Routes to libxr; reads coding-conventions.md: driver directory layout, `LIBXR_DRIVER` opt-in, minimal driver set, HPM rules (PLIC/IRQ wrapper, no SDK board helper calls); PR targets `dev`. |
| C2 | Can I change a driver's return value from `OK` to `BUSY` in one corner case? | Reads public-interface-checklist.md: this is a behavior delta; enumerate production consumers separately from tests; compare base/proposed behavior; declare it in the PR; requires maintainer approval before merge; candidate tests do not create the requirement. |
| C3 | How do I wire CI for a new Module repository? | module-development.md: the `module-ci.yml@v1` workflow used by BlinkLED/SharedTopicClient/CanIMU; context rules (PR uses the target branch, push uses the same-name branch or `dev`, tag uses `master`); manifest keys limited to `module_description`/`depends`/`standalone`. |
| C4 | Which branch does a PR target, and what goes in the description? | branches-and-releases.md: `dev` (never direct to `master`); description contains `Part of xrobot-org/XRobot-Dev-Roadmap#N` or `Closes ...`; notes `Closes` only takes effect when the merge lands on the default branch (`master`), at release time. |
| C5 | I changed the SPI public interface. What has to happen before this PR is ready? | public-interface-checklist.md full flow: write current behavior, production consumers, changed behavior; check all ten dimensions (returns/capacity, visibility/ordering, partial acceptance, blocking/timeout, completion/callbacks, buffer ownership, cancellation, context, compatibility/ABI, hardware side effects and Flash/RAM cost); PR declares every delta; maintainer sign-off. |
| C6 | Walk through releasing the next patch set (LibXR 2.0.2 / xrobot 1.0.2 / CodeGenerator 6.0.2). | branches-and-releases.md: the RELEASE.md sequence and `check_release.py`; release merges to `master` use merge commits and `dev` is fast-forwarded; tags are lowercase `v`; the three components release together with only the last digit bumped. |
| C7 | Make a BSP publish firmware automatically. | bsp-development.md: `bsp-stm32-ci.yml@v1` publishes on `v*` tags and auto-patches a tag on `master` push (STM32); MSPM0/HPM/CH32/Linux build without publishing; daily libxr-master canary on some platforms. |
| C8 | A generated file parses a `.ioc` pin wrong. Which repository gets the fix? | repo-map.md: parsing of vendor project files belongs to the CodeGenerator (xrobot-org/LibXR_CppCodeGenerator); PR/issue goes there, not to libxr or XRobot. |
| C9 | CI fails on a formatting check. | coding-conventions.md: clang-format 21.1.8 pinned; run the repo's format-check command locally first (the documented script/command), then push; format-only changes still go through `dev`. |
| C10 | Add a section to a documentation page. | website-docs.md: edit the Chinese page under `docs/` and the English mirror under `i18n/en/`; leaf URLs come from the parent directory plus the frontmatter `id`, not the file name. |
| C11 | Add a command to the VS Code extension. | tools-and-extension.md: `package.json` `contributes.commands`; release is a `.vsix` published through the GitHub Release workflow. |
| C12 | My PR merged but the Roadmap issue is still open. Is something broken? | branches-and-releases.md: expected when the merge landed on `dev`; `Closes` fires on the `master` release merge. |
| C13 | Run the LibXR host tests and state what a pass proves. | testing-and-acceptance.md: the documented host-test commands (test/automatic); a pass proves host-level behavior only — not hardware, DMA, or timing (evidence-level table). |
| C14 | Plan an on-board A/B test for a UART driver change. | testing-and-acceptance.md: two builds differing only in the change under test; run the baseline too; back up the flash before writing and restore+verify afterwards; the conclusion states whether the change is distinguishable. |
| C15 | While implementing a requested change you find an unrelated bug. Fix it in the same PR? | common-mistakes.md: findings outside the scope are reported, not fixed silently; a separate issue/PR or maintainer decision. |
| C16 | The request is "change the completion semantics of the UART driver". What is the first step? | workflow.md + public-interface-checklist.md: no source edits yet — a contract change; write current behavior, real production consumers and the changed behavior first, record a task contract with the before/after matrix, and get maintainer agreement in the issue or PR discussion before implementing. |
| C17 | During a review you notice a problem outside the reviewed scope. What do you do? | workflow.md Stages: the review stage only inspects and reports; the finding is reported, not fixed; a separate change or maintainer decision follows. |
| C18 | CI is green but the maintainer says the ownership design is wrong. What now? | workflow.md Reset rules: invalidate the candidate and the evidence that depends on it, return to design discussion and update the records, do not tail-patch; green CI, completeness and time invested do not override this. |
| C19 | The baseline and the candidate both pass your A/B test. How do you write the conclusion? | testing-and-acceptance.md: state plainly that the test cannot distinguish before from after; do not modify the code under test to force a baseline failure; when a group fails for both versions, trace the cause instead of blaming the tooling. |
| C20 | Asked to implement a change, may you also push the branch and open the pull request? | workflow.md Stages: no — implementation authority does not extend to delivery; push, PR and merge happen only when the person making the request explicitly asks. |
| C21 | Here is a design for a new feature. Ablate it. | workflow.md Ablation checks: go through each abstraction, component, state, indirection and side effect; justify each with a concrete requirement, production consumer or established fact; drop what cannot be justified; trace compensating parts to the root cause instead of keeping them; split concerns that fail independently; record results in the discussion ledger. |
| C22 | You changed what a callback argument means. How is this handled? | public-interface-checklist.md: the old call site must fail to compile or report an explicit error during generation or configuration (`static_assert`, deleted overload, explicit diagnostic); all known consumers migrate in the same change set; consumers that cannot migrate are listed for the maintainer before merge; silent meaning change is not allowed. |
| C23 | What do you do before flashing a board of unknown origin? | workflow.md Baseline and contamination + testing-and-acceptance.md: read out and keep a full-flash backup first, check the vendor flashing procedure against the chip manual and errata, and restore plus read back after testing. |
