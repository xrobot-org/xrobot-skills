When to read this: Creating a new BSP for LibXR/XRobot, or maintaining pins, presets, CI and firmware releases of an existing one.

# BSP development

A BSP is a board support package: a project that pairs a concrete board with the LibXR runtime and the XRobot module layer. A BSP repository combines four ingredients:

1. the vendor project — the board's own project files (a CubeMX `.ioc` project, a TI SysConfig `.syscfg` project, an HPM SDK application with a Pinmux Tool project, or a plain host program),
2. the LibXR Git submodule,
3. `Modules/` — the module request list (`modules.yaml`), the source list (`sources.yaml`), and the resolved `xrobot.lock`,
4. `User/` — the generated BSP objects plus the application configurations,

plus the CMake project with presets and the CI workflows.

Six public repositories cover the platform spectrum and serve as structural references:

| Repository | Platform | Vendor project form |
| --- | --- | --- |
| [bsp_stm32f103](https://github.com/xrobot-org/bsp_stm32f103) | STM32F103RCTx (BluePill) | CubeMX project, FreeRTOS |
| [bsp-dev-c](https://github.com/QDU-Robomaster/bsp-dev-c) | STM32F407IGHx (RoboMaster C board) | CubeMX project, FreeRTOS, one firmware per configuration |
| [bsp-mspm0g3507-mini](https://github.com/xrobot-org/bsp-mspm0g3507-mini) | TI MSPM0G3507 | SysConfig (`.syscfg`), bare metal |
| [bsp-hpm5301evklite](https://github.com/xrobot-org/bsp-hpm5301evklite) | HPMicro HPM5301 (RISC-V) | HPM SDK application + Pinmux Tool (`.hpmpc`) |
| [CH32V307_LibXR_Template](https://github.com/xrobot-org/CH32V307_LibXR_Template) | WCH CH32V307VC (RISC-V) | plain CMake project, FreeRTOS; LibXR template without a Modules layer |
| [bsp-linux-autoaim](https://github.com/QDU-Robomaster/bsp-linux-autoaim) | Linux host | host CMake program (auto-aim); the build output is an executable, not firmware |

## Anatomy

The vendor layer carries the board initialization and nests the LibXR submodule. CubeMX-based BSPs place the submodule inside the CubeMX tree (excerpt from `bsp_stm32f103/.gitmodules`):

```text
[submodule "Middlewares/Third_Party/LibXR"]
	path = Middlewares/Third_Party/LibXR
	url = https://github.com/xrobot-org/libxr.git
```

(excerpt.) The other platforms keep it at the repository root as `libxr/`, with the same URL. The submodule commit is the LibXR version pin.

The Modules layer holds the request list (excerpt from `bsp_stm32f103/Modules/modules.yaml`):

```yaml
xrobot: 1.0.1
modules:
- xrobot-org/BlinkLED@same-or-dev
```

(excerpt.) The top level accepts the keys `xrobot` and `modules` only. `Modules/sources.yaml` lists the module indexes (excerpt from `bsp_stm32f103/Modules/sources.yaml`):

```yaml
sources:
  - url: https://xrobot.work/xrobot-modules/index.yaml
    priority: 0
```

(excerpt; BSPs that consume a second ecosystem append its index with its own priority, as `bsp-dev-c` does for the QDU-Robomaster index.) After `xrobot setup`, the resolution lands in `xrobot.lock`, which is committed and starts with the header `# Generated by `xrobot setup`; do not edit by hand.`

The User layer holds the entry point and the configurations. `User/xrobot.yaml` is the default application configuration (excerpt from `bsp_stm32f103/User/xrobot.yaml`):

```yaml
modules:
  - module: xrobot-org/BlinkLED
    id: blink_led
    args:
      - led: LED
      - blink_cycle: 250
settings:
  monitor_sleep_ms: 1000
```

(excerpt.) Multi-product BSPs add further configuration files, for example under `User/RobotConfig/`.

Generated files come in two tiers, and the BSPs state this in their documentation:

- Generated and ignored by Git: `Modules/<owner>/<Repo>/`, `Modules/CMakeLists.txt`, `User/xrobot_main.hpp` (excerpt from `bsp_stm32f103/.gitignore`):

  ```text
  Modules/*/
  # ...
  # Generated by xrobot setup / xrobot gen
  User/xrobot_main.hpp
  Modules/CMakeLists.txt
  ```

- Generated and committed, with CI re-checking them: `User/app_main.cpp`, `User/app_main.h`, `User/flash_map.hpp`, `User/libxr_config.yaml`. Edits stay inside the `User Code` regions.

## Creating a BSP

CH32V307_LibXR_Template shows the platform layer of a minimal project. Its README lists the layout (excerpt from the CH32V307_LibXR_Template README; "LibXR 子模块" = LibXR submodule):

```text
User/app_main.cpp         LibXR 应用代码 app_main()
User/main.c               启动 FreeRTOS，创建运行 app_main() 的任务
Core/                     WCH 内核与系统文件、FreeRTOSConfig.h
startup_ch32v30x_D8C.S    启动文件
Peripheral/               WCH 外设库
FreeRTOS/                 FreeRTOS 内核与 RISC-V 移植
Link.ld                   链接脚本
wch-riscv.cfg             OpenOCD 配置（WCH-LinkE，SDI）
libxr/                    LibXR 子模块
```

The template is a pure LibXR project: it carries no `Modules/` directory and no XRobot configuration. An XRobot BSP is this platform layer plus the Modules and User layers below.

Platform starting points:

- STM32 — start from the CubeMX project (one `.ioc` at the BSP root). Run `libxr stm32 setup` in the BSP root: it generates `User/app_main.cpp`, `User/app_main.h`, `User/flash_map.hpp`, `User/libxr_config.yaml` and `cmake/LibXR.CMake` from the project, keeping the User Code regions. Rerun it after CubeMX regeneration or after changing a value in `libxr_config.yaml`; CI regenerates the same files and fails when they differ from the commit.
- MSPM0 — start from the SysConfig project (one `.syscfg` at the repository root). CMake runs SysConfig during configure and writes the output to `build/<preset>/syscfg/`, which stays out of the repository; changing the `.syscfg` regenerates on the next build. Regenerate the BSP objects with `libxr mspm0 setup -d .` (requires `MSPM0_SDK_INSTALL_DIR` and `SYSCONFIG_TOOL`). Buffer sizes and PWM frequencies live in `User/libxr_config.yaml`.
- HPM — start from an HPM SDK application plus a Pinmux Tool project `tool_config.hpmpc`. The SDK stays outside the repository (`HPM_SDK_BASE`); `pinmux.c/h` and `clock.c/h` are the tool's export output. Edit pin assignments in the Pinmux Tool GUI and re-export: files edited outside the tool cannot be re-imported. `User/app_main.cpp` is hand-maintained, and the HPM BSP carries neither `User/libxr_config.yaml` nor a generator pin.
- Linux — start from a host CMake program. There is no toolchain file; run `xrobot gen -c User/xrobot.yaml` before building.

Add the XRobot layer by running `xrobot init` in the BSP root. It creates `Modules/modules.yaml` (with the installed xrobot version as the `xrobot:` pin and an empty `modules:` list), `Modules/sources.yaml` (the official source), and `User/xrobot.yaml` (an empty configuration plus `settings: monitor_sleep_ms`), and appends the generated paths to `.gitignore` and the line-ending rules to `.gitattributes`. Then request modules with `xrobot module add <owner>/<Repo>` and run `xrobot setup` to resolve them into `xrobot.lock`.

## Fixed tool versions

Two pins fix the toolchain, plus the submodule:

- `xrobot:` — first line of `Modules/modules.yaml`, fixes the XRobot manager. Published BSPs pin the release versions (`xrobot: 1.0.1` at the baseline).
- `generator:` — first line of `User/libxr_config.yaml`, fixes the LibXR C++ CodeGenerator (PyPI package `libxr`). Published BSPs that carry the file pin `generator: 6.0.1` at the baseline (excerpt from `bsp_stm32f103/User/libxr_config.yaml`):

  ```yaml
  generator: 6.0.1
  terminal_source: usb_fs_cdc
  # ...
  ```

- The LibXR submodule commit fixes the library itself; the published BSPs and the CH32 template pin `5161373d` (LibXR v2.0.1) at the baseline.

Install the tools at the pinned versions and confirm with `xrobot --version`:

```bash
pip install xrobot==1.0.1 libxr==6.0.1
```

CI derives the versions from the pins instead of hard-coding them; the MSPM0 and HPM build workflows run (excerpt from `bsp-mspm0g3507-mini/.github/workflows/build.yml`):

```bash
pip install "xrobot==$(sed -n 's/^xrobot: *//p' Modules/modules.yaml)"
```

(excerpt.) `xrobot setup --frozen` — the mode CI uses — stops with an error when the installed xrobot differs from the `xrobot:` pin or the pin is missing.

## CMake presets and build commands

| Repository | Presets | Toolchain |
| --- | --- | --- |
| bsp_stm32f103, bsp-dev-c | `debug`, `relWithDebInfo`, `release`, `minSizeRel` | `cmake/starm-clang.cmake` (alternative `cmake/gcc-arm-none-eabi.cmake`) |
| bsp-mspm0g3507-mini | `debug`, `release` | `cmake/arm-none-eabi-gcc.cmake` |
| bsp-hpm5301evklite | `debug-flash-xip`, `debug-ram`, `release-flash-xip` | none; the SDK arrives via `HPM_SDK_BASE` |
| CH32V307_LibXR_Template | none | configured inside `CMakeLists.txt` (`COMPILER_PREFIX`) |
| bsp-linux-autoaim | `debug`, `relWithDebInfo`, `release` | none (host compiler) |

The embedded BSPs use Ninja with `binaryDir` `build/${presetName}`; firmware lands at `build/<preset>/<Project>.elf`.

Standard build sequences, with tool versions taken from the pins:

STM32 (`starm-clang` from STM32CubeCLT or the VS Code STM32Cube extension must be on `PATH`):

```bash
git clone --recursive https://github.com/xrobot-org/bsp_stm32f103.git
cd bsp_stm32f103
pip install xrobot==1.0.1 libxr==6.0.1
xrobot setup
cmake --preset debug
cmake --build --preset debug
```

MSPM0:

```bash
git clone --recursive https://github.com/xrobot-org/bsp-mspm0g3507-mini.git
cd bsp-mspm0g3507-mini
export MSPM0_SDK_INSTALL_DIR=<SDK directory>
export SYSCONFIG_TOOL=<SysConfig directory>/sysconfig_cli.sh   # sysconfig_cli.bat on Windows
pip install xrobot==1.0.1 libxr==6.0.1
xrobot setup
cmake --preset debug
cmake --build --preset debug
```

HPM:

```bash
git clone --recursive https://github.com/xrobot-org/bsp-hpm5301evklite.git
git clone --depth 1 --branch v1.13.0 https://github.com/hpmicro/hpm_sdk.git
export HPM_SDK_BASE="$PWD/hpm_sdk"
export GNURISCV_TOOLCHAIN_PATH=<toolchain directory>
cd bsp-hpm5301evklite
pip install xrobot==1.0.1
xrobot setup
cmake --preset debug-flash-xip
cmake --build --preset debug-flash-xip
```

CH32 (the container image carries the WCH toolchain):

```bash
git clone --recursive https://github.com/xrobot-org/CH32V307_LibXR_Template.git
cd CH32V307_LibXR_Template
docker run --rm -v "$PWD:/work" -w /work ghcr.io/xrobot-org/docker-image-ch32-riscv:main \
  bash -c 'cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j"$(nproc)"'
```

Linux (additionally requires OpenCV 4, Eigen 3, and HailoRT or OpenVINO per its README):

```bash
git clone --recursive https://github.com/QDU-Robomaster/bsp-linux-autoaim.git
cd bsp-linux-autoaim
pip install xrobot==1.0.1
xrobot setup
xrobot gen -c User/xrobot.yaml
cmake --preset release
cmake --build --preset release --target rm_auto_aim
```

Multi-product BSPs build one configuration at a time: run `xrobot gen -c User/RobotConfig/<config>.yaml` before building a non-default configuration. A single-configuration BSP builds without `gen`.

## CI

### STM32: the shared workflow

A STM32 BSP calls the shared workflow with its CMake project name and build type (excerpt from `bsp_stm32f103/.github/workflows/xrobot_stm32.yml`; the triggers are pushes to main/master/dev, `v*` tags, pull requests, and manual dispatch):

```yaml
jobs:
  build:
    # The release job of the shared workflow attaches firmware to releases, which needs write access.
    permissions:
      contents: write
    uses: xrobot-org/XRobot/.github/workflows/bsp-stm32-ci.yml@v1
    with:
      project: BluePill
      build-type: Debug
```

(excerpt.) `project` is the CMake project name and the firmware ELF base name. Multi-product BSPs list their configurations (excerpt from `bsp-dev-c`'s workflow; the real list has one line per `User/RobotConfig` file):

```yaml
    with:
      project: DevC
      configs: |
        default
        aerial
        # ... one line per configuration
```

(excerpt.) `default` maps to `User/xrobot.yaml`; every other name maps to `<config-dir>/<name>.yaml`. Further inputs of `bsp-stm32-ci.yml@v1`: `config-dir` (default `User/RobotConfig`), `toolchain` (default `cmake/starm-clang.cmake`), `build-type` (default `Release`), `presets` (for BSPs with multiple images), `release-configs` (the subset to publish; empty means all, or `default` when it is the only one), and `image` (default `ghcr.io/xrobot-org/docker-image-stm32:main`).

The check job:

- installs the pinned tools, reading `xrobot:` from `Modules/modules.yaml` and `generator:` from `User/libxr_config.yaml`;
- regenerates `User/app_main.cpp`, `User/app_main.h`, `User/flash_map.hpp` and `User/libxr_config.yaml` with `libxr parse` and `libxr gen --xrobot`, and fails when they differ from the commit;
- rejects text files stored with CRLF;
- runs `xrobot format --check`;
- runs `xrobot setup --frozen --context-ref <built ref> --release-ref <target ref>` — the release gate: a PR targeting `dev` requires locked module commits on the modules' `dev`, and `master` or a tag requires them on the modules' `master`.

The build job runs the matrix of configurations (and presets) and generates each non-default configuration with `xrobot gen -c` before building.

Branch model: `dev` receives changes; `master` receives only PRs from `dev`. The gate's `--context-ref`/`--release-ref` combined with the modules' `@same-or-dev` requests is what makes each branch build against the module branch of the same name.

### Firmware releases

The release job runs when a release is published, when a `v*` tag is pushed, or on a push to `master`/`main`. A `master` push whose commit carries no `v` tag is tagged automatically with the next patch version — the highest existing `vX.Y.Z` plus one, starting at `v1.0.0` — and published; a commit that already carries a `v` tag is released by that tag's own run. The published files per configuration:

- `<project>-<config>[-<preset>]-<tag>.elf` / `.hex` / `.bin`,
- the configuration copy `<project>-<config>-<tag>.yaml`,
- a reproducible `<project>-<config>-<tag>.tar.gz`,
- `SHA256SUMS`,
- `firmware-manifest.json` (schema 1: tag, commit, repository, project, tools, LibXR submodule commit, module commits, build sizes).

The release description is generated as a size table together with the tool versions. The calling workflow needs `permissions: contents: write`.

### Build-only platforms

The MSPM0, HPM, CH32 and Linux BSPs carry their own workflows and publish no artifacts:

- `bsp-mspm0g3507-mini` and `bsp-hpm5301evklite`: a check job (`xrobot format --check`, `xrobot setup --frozen`, with xrobot installed from the `modules.yaml` pin) and a build matrix over the presets, in `ghcr.io/xrobot-org/docker-image-mspm0:main` / `ghcr.io/xrobot-org/docker-image-hpm:main`.
- `CH32V307_LibXR_Template`: a build job running `cmake -B build -DCMAKE_BUILD_TYPE=Release` in `ghcr.io/xrobot-org/docker-image-ch32-riscv:main`.
- `bsp-linux-autoaim`: a build-test workflow with x86 and arm64 jobs.

The MSPM0, HPM and CH32 workflows add a daily compatibility canary: a `libxr-master` job on `schedule: cron "17 3 * * *"` (and on manual dispatch) moves the LibXR submodule to the head of LibXR `master`, rebuilds and reports. `continue-on-error: true` keeps a canary failure from failing the workflow. The Linux BSP covers two architectures instead, and the STM32 shared workflow contains no scheduled canary.

## Platform contracts

Some board-level obligations sit with the BSP because the library carries no guard for them. These hold for the platforms at the baseline versions.

- MSPM0 interrupts. SysConfig interrupt settings do not govern the LibXR drivers: the driver enables its IRQ sources and writes the NVIC priorities at runtime (values in the interrupt list of `references/coding-conventions.md`). Peripheral-versus-timebase ordering is set by the driver's runtime NVIC priorities: the timebase runs at the highest of the four priority levels this core exposes, with every peripheral below it.
- CH32 / QingKe V4 toolchain contract. Compile Zaamo-only, as `CH32V307_LibXR_Template/CMakeLists.txt` does (`-march=rv32imcf_zicsr_zifencei_zaamo -mabi=ilp32f -mno-save-restore`): `sc.w` on this core always succeeds, so `lr.w`/`sc.w` give no reservation and a compiler-generated CAS overwrites a concurrent publish. C-heavy ISRs, the FreeRTOS SysTick handler among them, take the generic `interrupt` ABI instead of `WCH-Interrupt-fast`, whose stack switch borrows `mscratch` and resumes from the wrong stack once the body needs a software frame. `ARCH_FPU=1` saves the task floating-point context, and `fence.i` follows any write of the global interrupt mask. Acceptance on the final ELF: no `lr.w`, no `sc.w`, no undefined `__atomic_*`.
- HPM GPIO controller choice. The FGPIO errata (E00037) is uncorrected, so it applies to every silicon revision of the family: use the regular GPIO controller. The library guard covers the interrupt APIs only — `HPM_FGPIO` returns `NOT_SUPPORT` there — while plain direction and level writes reach whichever controller the board file names; one GPIO0 instance escapes only because its address window does not overlap.
- HPM MCAN bus-off. The controller sets `CCCR.INIT` by itself on bus-off and on a message-RAM bit error, and only a CPU write of 0 clears it. A CAN driver added to this family carries the recovery path — clear `INIT`, wait for the protocol's bus-off recovery completion sequence, then re-drive the queued frames — otherwise the node stays offline until reset.
- STM32H5 cached OTP reads. With ICACHE enabled, a read of the OTP/RO window takes a BusFault. Enable the CubeMX cache-disable setting for that area, which configures a read-only non-cacheable MPU region ahead of ICACHE; reordering the ICACHE initialization dodges the fault and leaves the configuration wrong.
- STM32H5 GPDMA node type. Peripheral database `DB.6.0.161` forces a 2D node onto the GPDMA1 CH6/CH7 circular linked lists. A private 1D descriptor states `NodeType = DMA_GPDMA_LINEAR_NODE` and inherits request, direction and data widths from the CubeMX node rather than its node type.

## Pitfalls

- Keep install lines in sync with pins. A pin bump touches four places (LibXR submodule, `modules.yaml`, `libxr_config.yaml`, `xrobot.lock`) and the `pip install xrobot==… libxr==…` lines of the README in the same commit. Derive versions from `Modules/modules.yaml` and `User/libxr_config.yaml` when writing documentation, and update README install lines in the same commit as a pin bump.
- Line endings. Commit a `.gitattributes` with `* text=auto`, `*.sh text eol=lf`, `*.bat text eol=crlf`. The STM32 shared CI rejects text files stored with CRLF; remediate with `git add --renormalize .`. XRobot clones modules with `core.autocrlf=false` so the generated header digest matches across platforms.
- Submodules. Clone with `--recursive`; after a plain clone run `git submodule update --init --recursive`; CI checks out with `submodules: recursive`. The LibXR submodule commit is the library version pin and moves only as part of a release update.
- Generated files. `User/xrobot_main.hpp`, `Modules/CMakeLists.txt` and the module checkouts are generated and ignored; `User/app_main.cpp`, `User/app_main.h`, `User/flash_map.hpp` and `User/libxr_config.yaml` are generated, committed and checked by CI — edit only the User Code regions. `xrobot.lock` regenerates through `xrobot setup`.
- HPM configuration hygiene. `tool_config.hpmpc`, `pinmux.c/h` and `clock.c/h` are Pinmux Tool output; edit in the GUI and re-export. Keep BSP pins in one `init_bsp_pins()` group, and call `init_board_clock()` before `init_bsp_pins()` — calling `init_bsp_pins()` before the clock initialization loses GPIO direction and level writes.
- Configuration selection. The CI generates every listed configuration before building it; mirror that locally for multi-product BSPs with `xrobot gen -c <config>`.
